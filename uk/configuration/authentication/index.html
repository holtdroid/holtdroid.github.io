Configuration

Authentication

Sign-in modes — anonymous names, a shared password, OIDC, a forward-auth proxy, or users with passkeys and invite links.

Цей контент ще не доступний вашою мовою.

Holtdroid always knows who owns a session, but how people sign in is up to you. Pick one mode with auth.mode.

Mode Who gets in Identity
anonymous Everyone who can reach the URL (default) A random name like big-cute-otter
password Everyone who knows one shared password A random name, assigned after the password
oidc Users of your identity provider Username, name, email and groups from the IdP
users People with an invite link and a passkey A user in the api’s database, with a role
header Whoever your forward-auth proxy lets in Taken from headers the proxy sets
none Everyone, as one local admin local — for development only

Signed session cookies

Section titled “Signed session cookies”

anonymous, password, oidc and users keep the signed-in identity in an HttpOnly cookie holding a JWT signed with auth.sessionKey. Nothing is stored on the server, so any number of api replicas can verify it and it survives restarts and rescheduling — as long as they all share the same key.

Caution

Without sessionKey the api generates a random key at startup and warns: every restart signs everybody out and each replica rejects the others’ cookies.

The same key encrypts the Figma tokens users save on the Pixel perfect page (see Pixel perfect); with mode: header it is optional and used only for that.

The cookie is marked Secure when publicURL starts with https://. Switching modes invalidates existing cookies.

Anonymous

Section titled “Anonymous”

Visitors are signed in on their first request with a random size-mood-animal name, so everyone can tell whose session is whose without accounts. Get a new name in the user menu draws another one.

Shared password

Section titled “Shared password”

The sign-in page asks for the password once, then hands out a random name just like the anonymous mode. Failed attempts are slowed down.

OIDC

Section titled “OIDC”

Any OpenID Connect provider works (Authelia, Keycloak, Authentik, Dex, Google, Entra ID, …). Holtdroid uses the authorization code flow with PKCE and reads the user’s claims from the ID token and the userinfo endpoint.

Register the client at your provider with:

  • redirect URI https://<publicURL>/api/v1/auth/oidc/callback (override with auth.oidc.redirectURL);
  • grant type authorization_code, PKCE S256;
  • token endpoint authentication client_secret_basic.

Users and passkeys

Section titled “Users and passkeys”

The users mode keeps its own user directory in the api’s database. People sign up through an invite link with their name and email and sign in with a passkey (Touch ID, Face ID, Windows Hello, a security key or a password manager); there are no passwords. Admins get a Users page: everyone’s role, limits and passkeys, invite links, recovery links, and the people waiting for approval.

Caution

With the in-memory database every restart forgets all users and passkeys. Use database.type: sqlite, ideally with a replica.

The first admin. While there is no admin, the api logs a single-use invite link with the admin role at startup, valid for 24 hours. Open it, enter your name and email and register a passkey. Every restart replaces the link until the first admin exists:

Roles. admin manages users and sees the inventory and the audit log, user launches devices, and an empty role means waiting for approval: the person is signed in but sees only a waiting screen until an admin gives them a role. Holtdroid keeps at least one admin.

Invite links. An admin creates them on the Users page with a role, single-use or reusable, expiring after a day, a week, a month or never, and optionally limited to some email domains (on top of allowedDomains). A reusable link with the waiting for approval role is an open sign-up page whose newcomers you approve by hand. Each link stays in the list with a copy button until it expires or is used up; revoke it there when it leaks.

Creating users. Instead of an invite, an admin can add someone directly with New user on the Users page: name, email and role. The account starts without a passkey, and the dialog shows a single-use link, valid for an hour to 30 days (a week by default), that you send them; opening it registers their first passkey and signs them in. It is a recovery link, so a lost one is replaced from the user’s page.

Domains. allowedDomains and an invite’s domains check the email’s domain when someone signs up, but nothing sends mail to verify the address: treat the check as a guard against typos and the wrong people using a shared link, not as proof of who someone is.

Passkeys and recovery. Under Account and passkeys in the user menu, people add more passkeys, rename them and remove them; the last one stays. An admin can remove any passkey and create a recovery link, single-use and valid for up to 30 days, with which the user registers a new passkey on a new device. Creating one cancels earlier recovery links.

From the command line. holtdroid users runs in the api’s container, writes to the api’s database file and leaves replicating the change to the running api. It is for operators who can already exec into the api:

create adds a user without a passkey, such as a bot or an AI agent, which then calls the API with a cookie from session:

A session lasts auth.sessionTTL (--ttl to change it) and ends early when the user is deleted.

Signing in with SSO as well. Set auth.oidc as for the oidc mode and the sign-in page also offers Sign in with SSO. The provider’s email finds the user; an unknown email signs up with auth.users.oidcRole, or as admin when the user is in one of auth.adminGroups. allowedDomains applies to SSO sign-ups too. After that the role comes from the Users page, not from the provider’s groups.

Limits

Section titled “Limits”

Every user has five limits. An admin can set them per user on the Users page; an empty field uses the role’s default from auth.users.limits, and a role without one uses the server-wide setting.

Limit Server-wide setting Meaning
maxSessions sessions.maxPerUser Devices the user may run at once; 0 for no limit
maxSessionTTL sessions.maxTTL How long a session lives before it is reaped
recordingsQuota recordings.quota Storage for the user’s recordings; 0 for no limit
appDataMaxSize appData.maxSize Largest app data save; 0 for no limit
referencesQuota pixelPerfect.quota Storage for the user’s Pixel perfect references; 0 for no limit
mediaQuota media.quota Storage for the user’s media library; 0 for no limit

Deleting a user signs them out at once and removes their passkeys. Devices they run keep going until stopped or reaped, and their recordings, app data and references stay until they expire; their media library stays until an admin deletes it from the storage.

Forward-auth headers

Section titled “Forward-auth headers”

With mode: header Holtdroid trusts identity headers set by a proxy in front of it, and refuses requests without them.

Danger

The api must then only be reachable through that proxy — anyone who can reach it directly can claim any identity.

Authelia sends Remote-Groups comma-separated, which is what Holtdroid expects.

Groups and admins

Section titled “Groups and admins”
Key Applies to Meaning
auth.allowedGroups oidc, header If set, only members of these groups get in
auth.adminGroups oidc, header Members can stop and extend anyone’s sessions

In the users mode roles come from the directory instead; adminGroups only decides the role of a first SSO sign-in.

Everyone can see all sessions. Only the owner or an admin can stop or extend one.

Avatars

Section titled “Avatars”

When the identity provider supplies a picture (the OIDC picture claim, or header.picture in the header mode), the UI shows it. Otherwise — and in the anonymous and password modes — it draws a deterministic DiceBear Voxel Art avatar from the username, in the browser, so big-cute-otter always gets the same little voxel figure. Only absolute http(s) picture URLs are accepted.
